# Ingot engineering instructions

## Product and non-negotiable boundaries

Ingot organizes recipe versions, experiment records, and run evidence to support quality analysis, process analysis (including process diagnosis), and recipe optimization. Preserve the evidence chain from actual runs and reviewed quality results through optimization observations, recommendations, engineer decisions, execution links, and frozen outcomes.

- Platform owns formal business records and enforces authorization and business rules. Edge accepts standard events and buffers delivery. Optimizer performs numerical work without owning formal business state. Agent uses authorized read-only analysis tools and cites evidence. Web presents the workflow and its state.
- Engineers decide whether to use a recommendation. Ingot does not automatically apply recommendations to equipment. An LLM explains evidence and must never generate numerical process settings. Site equipment, procedures, and safety controls remain under the site's authority.
- Keep site-specific protocols, mappings, vendor SDKs, and integration policy outside the core. A new core capability needs a real deployment scenario, a user-facing path, and tests. Keep customer data, credentials, and unauthorized run evidence out of the public repository, fixtures, screenshots, and logs.

## How to work

Keep work anchored to the engineer's path from actual runs and quality results through analysis, recipe recommendations, decisions, and later outcomes. For a proposed change or review finding, identify the specific user task, observed problem or deployment requirement, impact, and a way to verify improvement. Prioritize defects that block this path or change its result. Separate confirmed defects from hypotheses and field-dependent needs. Use the simplest change that addresses the evidence, reuse existing capabilities, and defer speculative features or infrastructure until a concrete scenario warrants them. Apply security and reliability work in proportion to the actual deployment, impact, and stated requirements.

Use [the engineering foundation](docs/engineering-foundation.en.md) ([中文](docs/engineering-foundation.md)) as the theory reference. [ISO/IEC/IEEE 15288](https://www.iso.org/standard/81702.html) supplies the lifecycle framework and the V model connects requirements and design to verification. Verification checks specified behavior. Validation checks whether it serves the intended users in their actual conditions. Revisit requirements and design when verification or field evidence exposes a faulty assumption.

1. **Understand the change.** Read applicable directory instructions and inspect the existing entry point, contracts, tests, and relevant references below. Identify the actor, task, expected outcome, scope, constraints, and current behavior. Decide how the result will be observed, including applicable denial, failure, and insufficient-evidence cases.
2. **Choose a design.** Trace the use case through authorization, business rules, storage or computation, and user feedback. Identify the owner of each rule and record, the transaction or delivery boundary, and the failure behavior. Compare viable options when the change affects public contracts, data ownership or migration, site isolation, evidence admission, analytical outputs, or operational guarantees. Record the selected option, tradeoff, assumptions, and verification in the issue, PR, or owning design document as applicable.
3. **Implement and verify.** Make a focused change through the actual entry point. Run the checks that cover its behavior and affected boundaries. Report what changed, which checks ran, and which assumptions or validation remain open. Apply the relevant sections only. A small fix usually needs a clear expected result and a focused check. A cross-module or high-risk change needs explicit evidence for the affected boundaries.

Read [system design](docs/design.en.md) for the current architecture baseline, boundaries, and design questions under review. Use [current status](docs/status.en.md) and verify implemented behavior against code, SQL migrations, configuration, and tests. Consult the repository [Issues](https://github.com/liuweichaox/Ingot/issues) for tracked work. Distinguish product requirements and safety or authorization invariants from architectural choices, documented exceptions, and incidental implementation details.

When asked to review or improve the design, evaluate existing choices, assumptions, and documented exceptions against the user need, relevant engineering methods, and evidence. Use the current architecture as one candidate. Identify mismatches among the documentation, code, and tests. Compare alternatives and record the expected benefit, tradeoffs, migration impact, and how to verify the decision. When implementing an evidence-backed redesign within scope, update the design and affected contracts, code, tests, and gates together. Keep safeguards in effect throughout the transition.

For complex development, use multiple agents by default when the tool supports it. Plan first, then use read-only exploration to identify facts, contracts, rules, and risks. Assign disjoint files to implementers and include independent review or targeted verification where useful. Use only the roles the task needs. A single agent is sufficient for routine work.

## Software design and system architecture

- Apply domain-driven design, separation of concerns, and information hiding. Use domain terms and group rules that change together. Define state transitions, their preconditions, who can perform them, and how corrections preserve history. Extend the existing owner when it already represents the use case. Add an abstraction when it isolates a real dependency or separates responsibilities with different reasons to change.
- Apply the current ports and adapters boundaries when extending the existing design. Keep domain and Agent abstractions independent of databases, model providers, and equipment protocols. API handles transport and access checks, Application owns use-case policy, and Infrastructure implements persistence and integrations. Treat registered exceptions in [system design](docs/design.en.md) as reviewable debt with documented scope and exit criteria.
- For consequential architecture changes, use a lightweight form of [Attribute-Driven Design (ADD)](https://www.sei.cmu.edu/library/attribute-driven-design-add-version-20/). Prioritize the quality attributes the change must satisfy, such as data integrity, site isolation, recovery, or latency. For each material driver, state the initiating event, operating conditions, expected response, and a measurable acceptance criterion. Identify the affected elements and compare the current design with viable changes. Choose tactics, assign responsibilities, and define interfaces based on those criteria. Record the choice and its verification in the issue, PR, or design record. Use a C4 view or sequence diagram when it clarifies the design.
- For changes with competing quality goals, use the [Architecture Tradeoff Analysis Method (ATAM)](https://www.sei.cmu.edu/library/the-architecture-tradeoff-analysis-method/) as a review guide. Walk the prioritized scenarios against the proposed design. Record which goals improve, which incur a cost, and what risks or assumptions still need evidence. Split a deployment only when independent scaling, isolation, security, or lifecycle needs justify the new operational and consistency costs.
- Use the [System Design Primer](https://github.com/donnemartin/system-design-primer) as the main external reference for distributed-system options such as queues, storage, consistency, and backpressure. Use [System Design Notes](https://github.com/liquidslr/system-design-notes) for worked examples such as rough capacity estimates and queue design. Start from Ingot's workload, failure assumptions, and existing contracts before applying an example. Verify guarantees against primary documentation and repository tests. Require workload or failure evidence before introducing a new infrastructure dependency.
- Choose synchronous calls when the caller needs the result immediately and the dependency fits the latency and failure budget. Choose durable background work when completion can be deferred and work must survive interruption. Specify acceptance and completion semantics, timeouts, retries, idempotency, ordering, and what the user sees while waiting. For Edge and event changes, verify reconnect, duplicate and late events, and the documented acknowledgment behavior. See [data integration](docs/data-connection.en.md) and [production architecture](docs/production-architecture.en.md).
- For an Edge delivery tradeoff, estimate backlog from the site's event rate and supported offline window, and account for storage headroom and replay time. Compare any new queue or store with the existing durable outbox and Platform ingestion path. Test a lost acknowledgment after a Platform commit, then replay the same batch. Within the documented idempotency window, verify that accepted events produce no duplicate formal effects. Use deployment requirements for numerical targets and identify any targets that still need measurement.
- Check all affected contract producers and consumers, including .NET, Python, TypeScript, and site adapters. Preserve compatible identities, units, error codes, and behavior, or define an explicit version and migration path. Follow the repository's structured errors and bounded pagination conventions where applicable.

## Relational modeling and migrations

- Start by defining what one row means, who owns the write, the business key, site scope, relationships, and lifecycle. List the invariants and queries it must support. Find the authoritative record in the [data model](docs/data-model.en.md) and [ordered migrations](src/platform/Ingot.Platform.Infrastructure/Migrations/sql) before adding storage.
- Choose a typed column for a stable fact with the same owner and lifecycle. Use a related table for repeated values, relationships, or facts with independent identity, lifecycle, permissions, or history. Use versioned JSONB for a bounded variable payload or frozen snapshot when its contents do not require relational enforcement. Keep identity, scope, joins, and durable constraints explicit. Use a query or view for derived values by default. Persist a projection when measured workload or reproducibility justifies it and define how it stays current and can be rebuilt.
- Normalize around the owner of each fact and preserve append or supersede behavior where required. A recommendation, engineer decision, later run link, and frozen outcome have different lifecycles and retain separate records. Specify nullability, units, precision, time semantics, retention, and deletion behavior as applicable.
- Pair server authorization with database integrity. Use applicable keys, foreign keys, checks, and transaction boundaries. Include site scope in relationships where ownership requires it. Define the idempotency key and collision behavior for retried writes. Verify applicable invalid associations, duplicates, and concurrent updates against real PostgreSQL behavior. See [PostgreSQL 17 constraints](https://www.postgresql.org/docs/17/ddl-constraints.html).
- Derive indexes from real filter, join, sort, and cardinality patterns. Compare query plans on representative sanitized data and account for write, storage, and maintenance cost. See [PostgreSQL 17 query plans](https://www.postgresql.org/docs/17/using-explain.html).
- Add a forward migration and preserve committed, checksum-protected migrations. Verify fresh installs and upgrades with existing rows. For a risky schema transition, consider expand–migrate–contract, including compatibility of overlapping versions, bounded backfill, lock impact, integrity checks, and recovery from partial completion. Use the [deployment guide](docs/deployment.en.md) to plan backup, restore, or forward recovery.

## Evidence, process analysis, and optimization

- Use measurement science and data lineage. Keep intended settings, actual readings, trajectories, and quality results distinct. Preserve source, units, identity, time, versions, scope, and review state where they affect interpretation. Admit observations through the existing evidence assembly and admission rules. Surface missing, conflicting, rejected, or out-of-scope evidence and its reason.
- Use experimental design and statistical inference to evaluate comparability, measurement uncertainty, independent repetitions, and confounding. Distinguish observed facts, statistical associations, hypotheses, and supported causal claims. State assumptions, uncertainty, and applicability. Treat minimum sample counts as entry criteria.
- Use constrained optimization and decision theory to choose a method suited to the objective, adjustable variables, and available data. Check model applicability, observed coverage, and site-confirmed safety constraints separately. Preserve the applicable inputs, constraints, versions, and random seed. Stop or degrade as defined by the contract when required evidence or constraints fail. See [analysis and optimization](docs/optimization.en.md).
- For analytical changes, compare a suitable baseline against a versioned snapshot and retain eligibility and exclusion criteria. Use only information available at each decision point during historical replay. Verify numerical tolerances, reproducibility, and constraint behavior. Limit claims to what the evidence establishes. Site applicability, safety, and benefit require separate field evidence. See the [pilot guide](docs/pilot.en.md#field-evaluation-and-data-confidentiality).

## Security, safety, and AI behavior

- Apply least privilege and threat modeling to changes in trust boundaries, identities, data flows, and external services. Resolve site access server-side before applying recipe or other business filters. Verify permitted and denied operations at the relevant boundary. Apply NIST SSDF practices appropriate to the change and follow [SECURITY.md](SECURITY.md) for reporting.
- Select a risk technique that fits the scenario. Use FMEA for component or data failures and STPA for potentially unsafe interactions between people, software, and equipment. When the consequences matter, describe the failure, impact, control, residual risk, and verification. Examples include mismatched units, stale constraints, missing feedback, and mistaking a suggestion for an approved setting.
- For Agent changes, apply NIST AI RMF practices from the engineering foundation. Treat retrieved content as evidence, enforce tool and retrieval permissions, and check citation accuracy, source review and applicability, conflicting evidence, and the insufficient-evidence response. Keep numerical decisions and formal records on their designated business paths.

## User interface and interaction

- Use human-centered design and task analysis. Begin with the engineer's task and what they need to see, decide, and do next. Fit it into existing navigation, reuse workbench components, and show site, run, and recipe scope where relevant. Use process-engineering language and controls that correspond to the business action.
- For workbench visuals, start with the [shared UI components](apps/platform/src/ui/components.jsx), [implemented styles](apps/platform/src/styles/global.css), and [brand guide](docs/brand.en.md). When documenting reusable visual rules for coding agents, use [Google's DESIGN.md format](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md) as a reference for tokens and usage guidance. Derive those rules from Ingot's own UI and keep them aligned with the implementation.
- Use visual hierarchy and progressive disclosure. Give the current state, decisive evidence, and next action priority. Keep secondary details nearby. Show units, time ranges, missing values, and comparison context on charts and tables. Reinforce status colors with labels.
- Model the applicable interaction states, including loading, empty, insufficient evidence, denied, pending, failure, and completion. Say what happened and give the next useful action. Preserve inputs through recoverable failures when safe. For consequential actions, show the target and effect before commitment. Use server-side idempotency where duplicate submission could create another business record.
- Prefer native controls or established accessible widgets. Check keyboard operation, accessible names, focus visibility and restoration, status announcements, and representative viewport sizes and data lengths. Use [WCAG 2.2](https://www.w3.org/TR/WCAG22/) and [W3C ARIA patterns](https://www.w3.org/WAI/ARIA/apg/). Exercise the workflow with realistic data and roles, and use feedback from representative users for substantive changes.

## Writing and reviewing code

- Follow `.editorconfig` and the conventions of the owning module. Prefer straightforward control flow, descriptive names, small cohesive changes, and existing domain types and helpers. Introduce a new abstraction or dependency only when it removes a demonstrated responsibility or duplication. Avoid unrelated formatting churn; when a local convention is unclear, choose one consistent with adjacent code and apply it consistently within the change.
- Keep changes cohesive and local. Reuse existing rules, types, and conventions. Give functions and components clear responsibilities and make inputs, outputs, and errors explicit. Testable calculations should be independent of I/O where practical. Validate external input at boundaries and enforce business invariants at their owner. Make timeout, cancellation, retry, and partial-failure behavior explicit when crossing boundaries.
- Follow [`.editorconfig`](.editorconfig) and nearby code. Use UTF-8 and LF, four spaces for C# and Python, and two for JavaScript, TypeScript, JSON, and YAML. Use file-scoped C# namespaces, nullable reference types, PascalCase for C# public symbols and frontend components, and camelCase for ordinary locals and frontend functions.
- Make intent visible in names, types, test cases, module boundaries, and control flow. If a comment would restate what the code does, improve the code. Add a brief comment when an external constraint, design reason, or failure consequence would otherwise be easy to miss. Follow the concise public C# summaries, Optimizer API docstrings, and migration conventions in [Contributing](CONTRIBUTING.en.md).
- Review the final diff against the real entry point, business invariants, permissions, compatibility with existing callers and data, and behavior under failure. Keep each PR independently reviewable. Use concise imperative commits. Include the user problem, resulting behavior, significant tradeoffs, relevant contract and risk impact, checks, and deployment needs. Link relevant issues and include screenshots for UI changes.

## Test design and verification

- For bugs, reproduce with a failing test first. Use risk-based and layered testing. Unit-test rules and boundary values, integration-test real persistence, transactions and authorization, contract-test independently evolving components, and exercise critical end-to-end user paths. Assert visible behavior and durable effects. For database-specific guarantees, verify with a real database.
- Choose cases by equivalence classes, boundaries, and allowed or rejected state transitions. Cover applicable authorization, site isolation, retry, concurrency, upgrade, and failure recovery. Use user-visible roles and actions for UI tests, and reproducible fixtures, clocks, and seeds where appropriate. Use tests to support the claim being made.
- For example, evidence from a different run must not become an optimization observation. Verify the rejection and a matching case at the evidence assembly boundary. If the change exposes the rejection to an engineer, verify the message and next action in the workbench. Test the link against authorized site records before claiming that it works in a particular deployment.
- Run focused checks and lint affected frontend apps during iteration. Build the affected apps to verify changes to their output. Name tests `*Tests.cs`, `*.test.mjs`, and `*.test.jsx` for xUnit, node:test, and Vitest respectively. Run `git diff --check`. Run direct architecture, product scope, product language, and bilingual style checks for changes to architecture, product scope, public terminology, or documentation. Run the public documentation gate for C# changes.
- Run `./scripts/verify.sh` before opening a PR. It covers the repository gates, builds, tests, frontend lint and audits, observability, and Compose validation. Report executed checks, failures, and skipped checks with specific reasons. Field acceptance remains a separate verification activity with deployment evidence.

## Repository review

- For repository-wide reviews, record the revision and any working changes under review. Inventory user workflows, component boundaries, migrations, deployment steps, and public documentation. Prioritize paths where a defect could affect site isolation, evidence integrity, engineering decisions, or recovery. For a focused review, follow the affected paths and contracts.
- Trace critical workflows from the actual entry point through every relevant producer, consumer, and state change. Check the final business record and what the user sees. For example, if Platform aligns a candidate to a recipe step after Optimizer evaluates it, verify that the stored and displayed settings, predictions, and constraint assessment apply to the same candidate. Use a targeted cross-boundary test or replay when separate component checks leave that behavior unverified.
- Check public claims about current capabilities, defaults, and guarantees against the relevant entry point, configuration, migrations, tests, or operational evidence. Verify affected instructions through the commands and routes users actually use, including both languages when applicable. When documentation and behavior disagree, use the accepted requirement and available evidence to decide whether to correct the implementation, amend the claim, or flag a design decision for review. Use deployment or field evidence for claims about those conditions.
- Report findings with a location, observed behavior, expected behavior, impact, and supporting evidence. Call out test gaps and unresolved design questions separately from verified defects. Summarize the reviewed scope, the checks run and their results, and the important paths or claims that remain unverified with reasons. For fixes in scope, update the owning source of truth and add a focused regression check when existing coverage misses the defect.

## Documentation, delivery, and operations

- Plan and develop user information across the software lifecycle with [ISO/IEC/IEEE 26514](https://www.iso.org/standard/77451.html). Use [Diátaxis](https://diataxis.fr/) to classify task-facing technical content around learning, completing a task, looking up a fact, or understanding a design. Diátaxis guides content type and structure. It does not verify technical truth or prescribe every repository document. Review policies for clear scope, precedence, and actionable rules. Review design records for the decision, rationale, alternatives, and conditions that warrant revisiting it.
- Review and test user documentation with [ISO/IEC/IEEE 26513](https://www.iso.org/standard/89070.html) as a reference. Check accuracy, completeness, consistency, findability, and whether the reader can follow guidance and recognize success or recoverable failure. For important procedures, execute the published steps from the stated prerequisites and check the result. Apply the evidence checks in [Repository review](#repository-review) to claims about current system behavior and use deployment or field evidence for claims about those conditions.
- For a review of all repository documentation, inventory maintained Markdown files with `rg --files -g '*.md'`, including root and nested agent instructions, code and tool READMEs, policies, and public docs. Classify each file by audience, purpose, and authority before reviewing it. Check that its audience and task are clear, its scope and status are current, its claims have appropriate evidence, required steps and outcomes are complete, terminology agrees with source code and related docs, links and entry points work, and content is not duplicated or superseded. Apply the criteria that fit each type: task structure for user guides, priority and actionable wording for agent instructions, contracts and implementation for references, and rationale and reconsideration conditions for design records. For paired languages, compare meaning and behavior, not just headings. Give each reviewed file a disposition with evidence and distinguish confirmed defects from improvement opportunities and unverified claims.
- Keep one maintained home for each rule or procedure. Keep a standalone page when it serves a distinct task or needs its own entry point. Merge useful content that belongs with an existing task. Remove obsolete or redundant content after checking references and preserving required entry points. Follow [Contributing](CONTRIBUTING.en.md#verification-and-documentation) for bilingual maintenance, the catalogue, and retired routes. Follow the [brand guide](docs/brand.en.md) and use `apps/website/public/brand/` for canonical brand assets.
- For releases and operational changes, record affected versions, migration order, compatible configurations, readiness and failure signals, and the recovery path. Evaluate fault domains, retries, queue capacity, data integrity, and operational impact at representative load. Derive tolerated data loss and recovery time from the deployment scenario and verify them through exercises. Use `scripts/verify-production-acceptance.sh` for the field-production scope defined in the deployment guide.
- Feed incidents, regressions, and field results back into requirements, risks, and design. Record the observed impact and evidence. Update the owning rule, test, or runbook that prevents recurrence or makes it easier to diagnose.

## Repository map and commands

- `src/edge` contains intake and delivery. `src/platform` contains Platform API, workers, application policy, and persistence. `src/agent` contains analysis and evidence logic. `src/shared` contains shared .NET domain models and contracts. `optimizer/` contains numerical methods and their tests. `tests/Ingot.Core.Tests` contains xUnit tests.
- `apps/platform` is the React/Vite workbench. `apps/website` and `apps/docs-site` are Next.js apps. `docs/` holds product documentation, `deploy/` deployment files, `scripts/` verification and operations, and `tools/` benchmarks and utilities.
- From the root, use .NET SDK 10 for `dotnet restore Ingot.sln`, `dotnet build Ingot.sln`, and `dotnet test tests/Ingot.Core.Tests/Ingot.Core.Tests.csproj`. With Node.js 22.22+, install with `npm --prefix apps/platform ci` or substitute the relevant app directory. Use that prefix for `run lint`, `run build`, and `test`. The workbench starts on port 3000 with `npm --prefix apps/platform run dev`.
- For the Optimizer, use Python 3.12 and uv 0.12.5. Set up with `uv sync --project optimizer --extra service --group dev --locked`. Run Optimizer tasks with `uv run --project optimizer --locked ...`, including `pytest`.
- Start the application stack with `docker compose -f docker-compose.app.yml up -d --build` after setting up the environment in [getting started](docs/getting-started.en.md).
- Run direct gates with `bash scripts/verify-architecture.sh`, `bash scripts/verify-code-comments.sh`, `bash scripts/verify-product-scope.sh`, `bash scripts/verify-product-language.sh`, and `python3 scripts/verify-documentation-style.py`. The product language gate also runs the style check.
- On Windows, use PowerShell for native tools and WSL or another Bash environment with the required utilities for Bash gates. Keep Windows and WSL `node_modules` separate. If a line match fails, inspect checkout line endings with `git ls-files --eol` and report the environment used for verification.
