# 快速开始

> 文档状态：**当前操作指南**。本指南的目标不是立即运行优化器，而是先完成一条可追溯的“真实条件—过程—检验结果”记录。

## 选择使用路径

不需要从头完成所有步骤再看到系统。先根据目标选择路径：

| 目标 | 建议路径 | 结果边界 |
|---|---|---|
| 先评估界面和业务流程 | 使用下方[模拟数据快速预览](#模拟数据快速预览) | 只能验证页面和流程，不能证明真实工艺收益 |
| 不接真实工厂，复现优化方法链路 | 使用下方[公开数据实验效率验证](#公开数据实验效率验证) | 验证数据检查、分类隔离、历史池回放、基线比较和声明边界，不证明工厂收益 |
| 准备受控试点 | 从[准备环境](#1-准备环境)开始，按顺序完成一次代表性运行 | 需要真实或具有代表性的现场数据 |
| 准备生产部署 | 先读[生产架构](production-architecture.md)，再执行[部署运维](deployment.md)中的验收 | 必须独立完成备份恢复、故障、容量、告警和连续观察验收 |
| 参与开发 | 完成仓库安装后运行 `./scripts/verify.sh` | 适用于代码贡献，不替代现场验收 |

### 模拟数据快速预览

这条路径只需要 Node.js 22.22+，不需要数据库、设备或 Docker。首次运行先安装前端依赖：

```bash
npm --prefix apps/platform ci
```

在两个终端分别启动模拟 API 和前端：

```bash
# 终端 1：合成业务数据 API
node scripts/platform-demo.mjs

# 终端 2：连接模拟 API 的前端
npm --prefix apps/platform run demo
```

打开 `http://127.0.0.1:3001`，使用 `demo / demo` 查看工程师流程，或使用 `admin / admin12345` 查看系统管理和试点验收入口。模拟服务覆盖工艺配置、现场接入、生产运行、检验、追因、实验和多种状态，但所有数据均为合成数据。结束时在两个终端按 `Ctrl+C`。

### 公开数据实验效率验证

这条路径不需要数据库、设备或工厂数据，只需要 Git 和 uv 0.11.32。它使用仓库内明确许可、带 SHA-256 校验的固定 FDM 与混凝土公开数据，运行 14 个分层工艺上下文，并与随机选择和线性响应面比较：

```bash
./scripts/benchmark-public-validation.sh
```

结果写入 `artifacts/public-validation.json`。当前参考结果证明相对固定随机搜索减少追加实验，并与线性响应面总体非劣；不支持“优于所有 DOE/RSM 方法”的表述。快速检查、完整判定规则、数据许可和参考结果见[公开数据实验效率验证](https://github.com/liuweichaox/Ingot/blob/main/tools/public-validation/README.md)。公开数据可以验证软件与方法链路是否可复现，不能证明另一个工厂可以获得相同收益。

仓库还包含 v3 外部数据评估草案。它使用两个未参与 v2 开发的物理实验数据集，登记四个比较基线并加入机理特征消融。当前只执行完整性检查：

```bash
./scripts/verify-public-validation-v3.sh
```

草案协议不能运行完整效果评价。算法和协议提交冻结后，才使用 `./scripts/benchmark-public-validation-v3.sh` 生成首次结果。

## 1. 准备环境

推荐使用 Docker Compose 启动完整系统。需要 Git、Docker Engine 或 Docker Desktop，以及 Docker Compose v2；Compose 路径不要求主机预装 .NET、Node.js、Python 或 uv。

```bash
git clone https://github.com/liuweichaox/Ingot.git
cd Ingot
cp .env.example .env
```

修改 `.env` 中的数据库密码、Edge 上送令牌和管理员密码。至少把所有 `change-this-` 占位值替换掉；生产环境还必须使用随机生成、彼此不同的密码和令牌。

先校验 Compose 配置，再启动：

```bash
docker compose -f docker-compose.app.yml config --quiet
docker compose -f docker-compose.app.yml up -d --build
```

首次构建需要下载 .NET、Node、Python、PyTorch 和 TimescaleDB 镜像，可能持续数分钟。`up` 命令成功退出后检查容器状态：

```bash
docker compose -f docker-compose.app.yml ps
```

`postgres`、`optimizer`、`platform-api` 和 `platform-web` 应全部显示 `healthy`。然后检查：

```text
http://localhost:3000       工程工作台
http://localhost:8000/health
http://localhost:8100/ready
```

浏览器打开 `http://localhost:3000` 后，使用 `.env` 中的 `INGOT_ADMIN_USERNAME` 和 `INGOT_ADMIN_PASSWORD` 登录。若 `INGOT_ADMIN_PASSWORD` 留空，系统只在用户表为空的首次迁移引导中生成随机口令，可在 Migrator 日志中查找：

```bash
docker compose -f docker-compose.app.yml logs platform-migrate
```

Migrator 只在用户表为空时引导首个管理员。后续修改 `.env` 中的管理员密码不会重置已经存在的账户。

如果页面无法访问，先执行以下两条命令，不要反复重建或删除数据卷：

```bash
docker compose -f docker-compose.app.yml ps -a
docker compose -f docker-compose.app.yml logs --tail=200
```

若没有任何容器，说明构建尚未完成或已中断；若出现 `unexpected EOF`、`short read` 或拉取超时，通常是镜像下载不完整，直接重新执行 `up -d --build` 即可复用已完成层。更多诊断见[部署运维](deployment.md#启动与停止)。

如果只想评估文档和界面，可以使用模拟数据；如果要验证产品价值，必须最终接入真实或具有代表性的现场运行。

## 2. 先定义工程问题

选择一个边界清楚的问题，不要一开始把整条工厂都交给模型。至少明确：

| 内容 | 需要回答 |
|---|---|
| 工业对象 | 哪个产品、工艺或研发对象？ |
| 设备范围 | 哪台或哪组可比较设备？ |
| 运行边界 | 一次运行从哪里开始，到哪里结束？ |
| 可控变量 | 工程师实际能够改变哪些参数？ |
| 质量目标 | 用什么检验判断结果？方向、规格和单位是什么？ |
| 安全边界 | 哪些参数或结果不可越过？ |
| 上下文 | 哪些材料、工装、批次、校准或维护信息必须追溯？ |

变量、检验特性和单位使用稳定编码。显示名称可以改变，历史语义不能随意改变。

## 3. 建立工艺配置

工艺配置把该工艺的数据和分析规则放在一个版本中：

- 工艺数据模型和标准单位；
- 采集配置和设备点位映射；
- 执行边界、阶段号和过程特征；
- 检验定义和质量方案；
- 工艺规范变量、允许范围、目标和约束；
- 分析必需与有则记录的上下文字段。

先发布工艺配置版本，再让研发项目引用它。项目进入执行阶段后冻结所用版本与上下文策略，避免中途修改规则后无法解释历史观察。界面统一使用“工艺配置”；API 与代码契约仍使用技术名称 `ScenarioPackage`。

新建研发项目后，先在项目工作区完成“阶段 0：预注册与数据基线”：冻结数据范围、纳入排除、比较基线、主要与守门指标、停止和否证条件，并记录工程师当前流程的实际时间与步骤。系统会同步计算并固化该范围的数据可靠性快照。预注册必须由另一名项目成员复核；复核通过后“开始研发”才会启用。

## 4. 连接数据源

进入“工艺配置 → 配置总览”，检查数据标准、现场接入、分析规则、质量规则和配置发布的准备状态。连续过程数据源在“现场接入 → 数据源配置”中完成：

1. 注册现场节点与设备身份；
2. 选择协议并填写连接信息；
3. 将原始点位映射为稳定工艺变量；
4. 在目标 Edge 上探查和读取真实值；
5. 检查数据类型、倍率、偏移和单位；
6. 发布配置并确认 Edge 已实际应用；
7. 配置检验录入、仪器或质量系统来源。

不要把 PLC、仪器或网关地址直接写进研发项目。现场接入负责来源地址和协议，研发项目只引用稳定业务编码。

系统允许提前准备可复用起点。新建工艺数据字典时可应用精密模压示例；新建工装结构时可应用“上模芯、下模芯、模架”结构示例。它们只负责预填结构，必须结合本厂设备、仪器、视觉系统或 MES 的真实字段完成连接验证和版本发布。首台同类设备验证通过后，还可以提取版本化任务模板、数据源实例和任务绑定，用于后续批量接入。

详细协议语义见[数据接入](data-connection.md)。

## 5. 建立生产上下文

在生产上下文中确认当前设备对应的：

- 产品或工艺对象；
- 已发布工艺规范版本；
- 已装工装及组合版本；
- 场景要求的材料批次、组件、校准或维护信息。

这些信息在运行开始时固化为快照。不要等质量异常后再手工补写“可能使用了哪套工装总成”。

## 6. 完成一次运行

一次运行需要稳定身份贯穿实验计划、现场执行和检验记录：

```text
研发 ExecutionKey ←→ Platform ExecutionId
```

两者可以使用同一个值，也可以使用确定性映射，但关系必须在执行前建立并可追溯。MES 工单、条码或仪器样本号可以承载映射；设备寄存器只作为外部参考，不替代 Edge 生成的 `ExecutionId`。

完成运行后，在“生产运行 → 运行记录”的运行详情中确认：

- 开始和完成事件齐全；
- 实际参数已经采集；
- 过程曲线和阶段可用；
- 运行上下文状态已解析；
- 配置和来源版本明确。

## 7. 关联检验结果

录入或接收该运行的质量与安全结果。每项结果至少包含：

- 检验特性编码和版本；
- 数值、判定和单位；
- 样本或运行身份；
- 时间、来源和必要附件；
- 需要时的复核状态。

平台当前只接受签名与扩展名一致的 PNG、JPEG、TIFF 或 PDF 检验附件；附件必须随当前授权 `SiteId` 上传，下载也会重新校验岗位和站点权限。

检验结果必须关联到同一次真实运行。无法唯一关联时保留待处理状态，不要按时间邻近自动猜测。

## 8. 检查数据可信度

在“工艺追因 → 数据可信度”和研发项目的“实验数据准备情况”中检查：

- 运行完整率；
- 实际参数覆盖率；
- 过程特征覆盖率；
- 运行—检验关联率；
- 分析必需上下文覆盖率；
- 单位、时间、配置版本和来源异常；
- 每条排除运行的具体原因。

常见排除原因包括运行未完成、实际设置缺失、过程数据不可用、检验缺失、单位不一致或上下文配置缺失。不要用计划值或手工猜测隐藏问题。

完成到这里，系统才真正从“采到了数据”进入“数据能够支持工程判断”。

## 9. 比较运行并形成候选

进入“工艺追因 → 追因工作台”，选择一次未达到目标的运行，并选择匹配条件明确的合格或历史基线。系统可以帮助查看：

- 首次偏离发生在哪个阶段；
- 实际设定与计划是否一致；
- 哪些轨迹特征差异最大；
- 材料、工装、设备或时间因素是否存在覆盖和混杂；
- 哪些候选能够通过下一次实验辨识。

观察分析只形成候选原因。工程师审核候选、反证、现场限制和数据不足后，再创建研发假设。

## 10. 设计验证实验

实验草案至少定义：

- 要验证的候选原因；
- 可控变量和候选条件；
- 对照、重复、区组和执行顺序；
- 目标、最小有意义效应和安全边界；
- 停止与回退条件。

可先选择经典 DOE 方法并预览完整运行表。预览仅帮助生成与检查计划，不会批准实验或下发设备参数；工程师可以修改运行、补充对照，并在检查清单通过后提交。

工程师批准后执行。全部运行和检验完成时，系统从源数据计算实验结果并将假设标记为支持、否决或仍不确定。

## 11. 需要时进入优化

当项目已有可信观察、明确可控变量和安全基线时，可以生成下一组实验建议。系统显示参数、目标预测区间、安全结果、综合可行概率、数据范围、模型版本和推荐理由。

需要使用机理知识时，先到“工艺研发 → 研发成果”选择项目，上传来源并完成声明审核与激活。变量按名称选择，单位由项目自动带入；产品、设备、工装和工艺规范适用范围从项目上下文中选择。被当前项目上下文匹配的声明可缩窄硬边界或参与软排序。实际采用记录不在独立“机理”页签中，而显示在项目“实验”表的“预测与可信度”列；只有优化实验确实采用声明时才出现展开面板。

同一批实验未完成前，待执行点用于避免重复建议。一个成功参数点只能形成候选设置；工艺操作域需要独立重复、边界或交互验证以及另一名工程师复核。
