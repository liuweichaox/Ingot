# 安装与第一个数据闭环

> 文档状态：**当前操作指南**。本指南的目标不是立即运行优化器，而是先完成一条可追溯的“真实条件—过程—检验结果”记录。

## 1. 准备环境

推荐使用 Docker Compose 启动完整系统。需要 Git、Docker Engine 或 Docker Desktop，以及 Docker Compose v2。

```bash
git clone https://github.com/liuweichaox/Ingot.git
cd Ingot
cp .env.example .env
```

修改 `.env` 中的数据库密码、Edge 上送令牌和管理员密码，然后启动：

```bash
docker compose -f docker-compose.app.yml up -d --build
```

检查：

```text
http://localhost:3000       工艺研发界面
http://localhost:8000/health
http://localhost:8100/ready
```

如果只想评估文档和界面，可以使用模拟数据；如果要验证产品价值，必须最终接入真实或具有代表性的现场运行。

## 2. 先定义工程问题

选择一个边界清楚的问题，不要一开始把整条工厂都交给模型。至少明确：

| 内容 | 需要回答 |
|---|---|
| 工业对象 | 哪个产品、工艺或研发对象？ |
| 设备范围 | 哪台或哪组可比较设备？ |
| 运行边界 | 一次运行从哪里开始，到哪里结束？ |
| 可控变量 | 工程师实际能够改变哪些参数？ |
| 质量目标 | 用什么检验判断结果？方向、规格和单位是什么？ |
| 安全边界 | 哪些参数或结果不可越过？ |
| 上下文 | 哪些材料、工装、批次、校准或维护信息必须追溯？ |

变量、检验特性和单位使用稳定编码。显示名称可以改变，历史语义不能随意改变。

## 3. 建立工艺配置

工艺配置把该工艺的数据和分析规则放在一个版本中：

- 工艺数据模型和标准单位；
- 采集配置和设备点位映射；
- 周期边界、阶段号和过程特征；
- 检验定义和质量方案；
- 配方变量、允许范围、目标和约束；
- 分析必需与有则记录的上下文字段。

先发布工艺配置版本，再让研发项目引用它。项目进入执行阶段后冻结所用版本与上下文策略，避免中途修改规则后无法解释历史观察。界面统一使用“工艺配置”；API 与代码契约仍使用技术名称 `ScenarioPackage`。

## 4. 连接数据源

在“数据与接入”中完成：

1. 注册现场节点与设备身份；
2. 选择协议并填写连接信息；
3. 将原始点位映射为稳定工艺变量；
4. 在目标 Edge 上探查和读取真实值；
5. 检查数据类型、倍率、偏移和单位；
6. 发布配置并确认 Edge 已实际应用；
7. 配置检验录入、仪器或质量系统来源。

不要把 PLC 地址直接写进研发项目。设备接入负责地址和协议，研发项目只引用稳定业务编码。

详细协议语义见[设备与数据接线](data-connection.md)。

## 5. 建立生产上下文

在生产上下文中确认当前设备对应的：

- 产品或工艺对象；
- 已发布配方版本；
- 已装工装及组合版本；
- 场景要求的材料批次、组件、校准或维护信息。

这些信息在运行开始时固化为快照。不要等质量异常后再手工补写“可能使用了哪套模具”。

## 6. 完成一次运行

一次运行需要稳定身份贯穿实验计划、现场周期和检验记录：

```text
研发 RunKey ←→ 现场 CorrelationId ←→ Platform OperationRunId
```

三者可以是同一个值，也可以使用确定性映射，但关系必须在执行前建立并可追溯。MES 工单、条码、仪器样本号或设备寄存器都可以承载映射。

完成运行后，在周期详情中确认：

- 开始和完成事件齐全；
- 实际参数已经采集；
- 过程曲线和阶段可用；
- 运行上下文状态已解析；
- 配置和来源版本明确。

## 7. 关联检验结果

录入或接收该运行的质量与安全结果。每项结果至少包含：

- 检验特性编码和版本；
- 数值、判定和单位；
- 样本或运行身份；
- 时间、来源和必要附件；
- 需要时的复核状态。

检验结果必须关联到同一次真实运行。无法唯一关联时保留待处理状态，不要按时间邻近自动猜测。

## 8. 检查数据可信度

在“数据质量”和研发项目的“实验数据准备情况”中检查：

- 运行完整率；
- 实际参数覆盖率；
- 过程特征覆盖率；
- 运行—检验关联率；
- 分析必需上下文覆盖率；
- 单位、时间、配置版本和来源异常；
- 每条排除运行的具体原因。

常见排除原因包括运行未完成、实际设置缺失、过程数据不可用、检验缺失、单位不一致或上下文配置缺失。不要用计划值或手工猜测隐藏问题。

完成到这里，系统才真正从“采到了数据”进入“数据能够支持工程判断”。

## 9. 比较运行并形成候选

选择一次未达到目标的运行，并选择匹配条件明确的合格或历史基线。系统可以帮助查看：

- 首次偏离发生在哪个阶段；
- 实际设定与计划是否一致；
- 哪些轨迹特征差异最大；
- 材料、工装、设备或时间因素是否存在覆盖和混杂；
- 哪些候选能够通过下一次实验辨识。

观察分析只形成候选原因。工程师审核候选、反证、现场限制和数据不足后，再创建研发假设。

## 10. 设计验证实验

实验草案至少定义：

- 要验证的候选原因；
- 可控变量和候选条件；
- 对照、重复、区组和执行顺序；
- 目标、最小有意义效应和安全边界；
- 停止与回退条件。

工程师批准后执行。全部运行和检验完成时，系统从源数据计算实验结果并将假设标记为支持、否决或仍不确定。

## 11. 需要时进入优化

当项目已有可信观察、明确可控变量和安全基线时，可以生成下一组实验建议。系统显示参数、目标预测区间、安全结果、综合可行概率、数据范围、模型版本和推荐理由。

同一批实验未完成前，待执行点用于避免重复建议。一个成功参数点只能形成候选设置；工艺窗口需要独立重复、边界或交互验证以及另一名工程师复核。

## 12. 演示场景

仓库中的光学镜片模压模拟器用于验证完整数据链，不代表真实设备地址或量产工艺窗口。它提供三菱 A-compatible MC 1E 二进制接口、阶段号、温度、压力、位置等过程量和配方参数。切换真机时应重新验证地址、量程、单位、周期边界和安全条件。

模拟结果只能证明软件路径可运行，不能证明系统已经缩短真实工艺研发周期。
