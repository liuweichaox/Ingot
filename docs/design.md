# 设计说明

## Ingot Chat 设计

```text
问题与当前页面信息
  → 类型化查询计划
  → 权限、范围与工具白名单校验
  → check_data_quality / get_cycle_trace
  → 数字与结果与原始记录核对
  → 流式回答
```

Chat 的模型负责语言理解和回答组织。Platform 的确定性代码负责数据查询、权限、工具执行、数字和结果与原始记录核对。Chat 运行按用户 隔离，只能通过 `/api/v1/chat/*` 访问。

## 事件接入设计

使用方将任意来源映射为 `ProductionEvent` 批次，并调用 `/api/v1/events:batch`。Platform 负责以下确定性工作：

1. 校验 Edge 令牌、`edgeId`、批次大小和事件字段；
2. 校验 `source` 前缀、事件 ID 与序号唯一性；
3. 以 `eventId` 和 `(edgeId, seq)` 处理重复提交；
4. 保存中心数据并返回 `ackSeq`；
5. 提供查询、SSE 和按 `correlationId` 的周期事件链。

数据源协议、现场缓存、重试时机和进程监管由使用方决定。标准契约避免把这些实现细节耦合到 Platform。

## 质量检验工作流

质量检验属于被分析运行的后续工作流，不把空白“检测录入”表单作为独立业务对象：

1. 离散生产可由 `cycle.completed` 生成周期质量任务；连续生产、运行段和物料批次通过显式质量范围绑定运行对象、起止时间和已发布 `InspectionPlan`；没有匹配方案时不臆造待检任务；
2. 方案引用版本化 `InspectionDefinition`，配置必检项目、顺序、原始附件和复核要求；操作人员选择任务后带入只读的质量对象和分析范围编号；
3. 原图先上传到受控长期存储，由服务端计算 SHA-256，再随检测记录保存引用；
4. 历史检测记录可重新打开原图并追加不可变的复核结论，原图访问和复核动作写入审计日志，派生缩略图不能替代原图；
5. 检测结果只表示观测结果，不等同于 QMS 放行或设备控制。

全局导航使用“质量检验”作为工作台入口；“新建检验记录”只是工作台中的动作。质量对象和分析范围只能来自待检任务，不提供手工伪造关联。检验提交、原图访问与复核统一使用 Platform 登录身份和角色，不设置检验专用用户或访问密码。

“质量方案”配置页维护检测定义和方案版本。已发布方案与检测定义版本不可覆盖；修改必须创建新版本。光学玻璃模压的视觉检查和人工终检只存在于可选样例配置，不是 Platform 默认规则。

角色由统一身份的声明提供：`quality.inspector` 可提交检测，`quality.reviewer` 可复核原图，`process.engineer` 可查询记录和历史比较，`platform.admin` 具有平台管理权限。开发环境可使用内置身份便于试用；生产环境必须由宿主认证建立用户身份。

## 运行对象与分析范围

Platform 不把“生产周期”作为所有工业数据的前提。事件中的 `subject.type + subject.id` 形成运行对象目录；对象可以是设备、产线、工位、传感器或使用方定义的其他类型。对象目录和数据健康页面直接从事件库聚合事件数、样本数、关联运行、首次/最近记录及最大采样间隔，因此连续运行对象即使没有周期也必须可见。

分析通过范围关联工艺数据和质量结果：

- `production-cycle`：有明确开始和结束的单件或单周期加工；
- `production-run`：有开始和结束、但可覆盖多件产品的运行段；
- `analysis-window`：连续数据中的明确时间窗口；
- `material-lot`：需要按物料批次组织的质量范围。

质量记录是一等数据，统一关联“分析范围 + 质量对象 + 检测定义版本”。质量分析读取有效检测记录，而不是从周期状态推测质量；因此周期检测和连续运行时间窗口可以在同一页面按产品、配方、运行对象和检测结果分层。

## 同系列历史周期比较

`GET /api/v1/cycle-comparisons/{correlationId}` 以一个周期为基准，只选择已发布分析方案规定的同类历史周期。开始和结束事件决定周期是否完成；过程数据另行标记为可用、降级或不可用。比较服务按真实时间戳计算整周期时间加权特征，遇到明显采样空窗时不跨空窗插值，并关联配方版本、检测结果及最新原图复核结论。正常周期权重为 1，降级周期权重为 0.5，不可用周期不进入正式统计。

分析方案使用 `stage-relative` 对齐时，`stage-relative-v1` 计算器按每条采样的 `process_phase` / `process_stage` 记录或 `recipe_step` 映射形成半开阶段区间。相邻同阶段采样合并为一个区间；同一阶段在周期中重复出现时保留独立顺序，不把两个区间混算。每个阶段特征携带阶段编码、顺序、来源、起止时间、有效时长和覆盖率；未归属采样、必需阶段缺失和未闭合边界进入数据质量限制。

周期比较同时按有效检测结果将周期分为合格组和不合格组，对同一“信号 + 阶段 + 阶段顺序 + 特征”计算两组中位数、稳健效应和候选分数。候选分数只用于排查排序；结果同时列出产品、设备、配方和模具等可能的混杂维度，并明确区分数据不足、探索性和稳定三个等级。普通历史关联不能写成已确认根因。

`stage-relative-v1` 由确定性计算器产生，并通过 `cycle_analysis_materializations`、`cycle_phases` 和 `cycle_features` 保存完成周期的结果。物化身份同时包含周期号、算法版本、工艺数据模型版本和分析方案版本；源事件最大摄入编号与事件数必须完全一致才能复用。新事件接入后，同一周期的已有物化结果立即标记为 `dirty`，下一次周期列表或历史比较按完整事件重新计算。活动周期保持查询时计算，不保存尚未封口的中间特征。物化不可用时服务降级为同一确定性计算器，不改变数值和结果核对规则。

## 全量记录与有界传输

Web 时间线和 Chat 周期分析不能以 500 条作为业务范围上限。API 可以继续按 500 条分页传输，但页面与确定性分析工具必须持续翻页直至范围结束。模型只接收全量数据计算后的有界摘要，不直接处理无限原始行。

## 隔离与恢复

- Chat 的创建、列表、读取、SSE 和取消均按用户 鉴权；
- SSE 使用单调事件序号，客户端通过 `Last-Event-ID` 恢复；
- 服务重启后，中断的 Chat 运行进入明确终态；
- 事件提交按批校验，调用方应保存已提交序号并基于 `ackSeq` 处理重试；
- Chat 不持有数据源凭据，也不调用现场网络或设备接口。
