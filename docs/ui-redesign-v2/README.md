# Ingot 前端重构设计规格 v2.2

> 面向 `apps/platform` 工程师工作台。定义**产品定位口径、信息架构、命名、按钮文案、布局与设计令牌**。
> 依据 `docs/brand.md`（定位与色板的唯一事实源）、`docs/design.md`（架构基线）、`docs/faq.md`（能力边界）。
> 配套交付：`ingot-prototype.html`（可点击原型）、`navigation.js` / `App.jsx` / `global.css`（导航层与令牌代码）。

## 0. 定位口径（一切设计的前提）

`brand.md` 已经写死：

| 项 | 原文 |
|---|---|
| 产品类别 | 开源工艺追因与优化系统 |
| 主要用户 | 负责**新产品、新材料和新工艺开发**的工艺、质量、设备和研发工程师 |
| 工作对象 | 一次真实运行的生产条件、过程轨迹、质量结果、工程判断和后续实验 |
| 标语 | **看清这次运行，优化下一次运行。** |

**它不是 MES。** 用产出物划界最清楚：

| 系统 | 产出物 | 管的是 |
|---|---|---|
| MES | 产量与进度 | 执行 |
| Historian / SCADA | 曲线 | 信号 |
| LIMS | 检测报告 | 样品 |
| QMS | 不合格处置与整改 | 合规 |
| PLM | 设计版本与 BOM | 设计 |
| JMP / Minitab | 一次分析结论 | 分析（数据靠手工喂） |
| **Ingot** | **有适用范围与失效条件的、经实验验证的工艺窗口** | **工艺参数为什么这么定** |

最接近的是 **DOE 统计软件 + 电子实验记录本**。相对它们的差异化：那类工具的可信度上限被
"人工录入"锁死；Ingot 自己去现场取真实运行事实，分析建立在"这确实是那一次运行"之上。
**采集不是产品，采集是让分析可信的前提**（`faq.md`：「Ingot 是数据采集系统吗？不只是。」）。

### 0.1 定位对界面的三条硬约束

1. **主战场是研发试制，不是量产。** 不做排班、交接班、人员编制、不合格品流程 —— 那是 MES / QMS。
2. **不硬编码任何上下文维度。** 界面上出现哪些上下文字段，完全由**场景包声明**决定。
   研发场景不声明"班次"，界面上就不存在这个概念；将来上量产线要按班次分层，
   在场景包里加一个字段即可，前端不改一行。
   （代价：一批页面要改成"按声明渲染"，不能再写死列。收益：换场景零前端改动，
   这正是 `design.md` 的场景替换边界要求的。）
3. **"执行人"要保留，而且比量产更重要。** 量产 N=2000，个人操作差异被平均掉；
   研发 N=15，一个人手法稳、一个人手法飘足以让结论翻转。它不该被优化、不该被归咎，
   但必须被记录，并在可比性检查里报警：出现的是「基线组 陈 6 / 李 2，对照组 陈 3」，
   而不是「白班转夜班」。

## 0.2 一句话结论

当前界面按**数据表和部门**组织；新界面按**工程师在回答哪个问题**组织。
一级导航从"工作台 / 生产运行 / 质量管理 / 工艺研发 / 数据与配置 / 系统管理"（6 个）
改为 **总览 · 课题 · 证据 · 追因 · 配置**（5 个），系统管理移出一级导航，
并引入三个当前完全缺失的结构：**全局分析范围轴**、**证据面板**、**对比暂存区**。

**课题是主线，所以排第二位** —— 产品的价值就是把一个工艺问题推到有适用范围的工艺窗口。
**证据是事实层**（运行 + 检测结果 + 事件 + 现场上下文），对应标识下方两块钢锭；
**追因把证据变成候选，课题把候选变成结论**，对应顶部金锭。标识释义直接成了信息架构。

## 1. 现有 IA 的六个结构性问题

| # | 问题 | 现状证据 | 后果 |
|---|---|---|---|
| 1 | **"数据与配置"是杂物抽屉** | 一个模块里同时装着「数据可信度」（每天用，分析活动）、「工艺配置」（季度用，建模活动）、「现场接入」（设备工程师用，IT 活动） | 三类用户、三种频次、一个菜单。谁都要点进去，谁都不认为这是自己的地盘 |
| 2 | **配置被拆散在三个模块** | `/configuration/*` 前缀的 12 个路由分散在「生产运行」（工装资产）、「质量管理」（质量规则）、「数据与配置」（工艺配置）下 | URL 命名空间说这是一件事，菜单说这是三件事。"配一个新工艺场景"要跨三个一级模块 |
| 3 | **证据链被模块边界切断** | 「周期对比」在生产运行、「质量追因」在质量管理、「工艺优化」在工艺研发 | `design.md` 明确写"追因与优化不是平行产品……它们必须读取同一份证据"，但导航把这条链切成三段 |
| 4 | **频次严重错配** | 「周期记录」（每天几十次）与「组件分类」（一年几次）在同一级 | 高频入口被低频入口稀释，工程师每天要跳过一堆用不到的项 |
| 5 | **命名不自洽** | 菜单「周期记录」→ 页面标题「运行记录」；菜单「工艺优化」是「工艺研发」模块的子项，父子重名；「工业对象」抽象到无法判断该不该点 | 术语在菜单、标题、正文里漂移，用户建立不起稳定的心智模型 |
| 6 | **缺少贯穿全局的"范围"概念** | 每个页面各自带筛选器，切页面就丢失 | 系统的全部价值建立在"同一次真实运行""可比运行""因素重叠"上，但界面没有一个地方承载"我现在在看哪一批数据" |

> 补充：`design.md` 已把"Web 菜单与页面布局"列入**可演进策略**，明确不属于不可变架构。
> 因此本次重构不触碰业务记录边界、运行身份、实验状态机与 Optimizer 无状态协议。

## 2. 新信息架构

### 2.1 一级导航（5 个模块）

顺序本身就是产品叙事：**先看今天要做什么 → 打开手上的课题 → 查它的证据 → 找差异 → 系统怎么理解这条产线。**

| 顺序 | 模块 | 层 | 回答的问题 | 图标 |
|---|---|---|---|---|
| 1 | **总览** | — | 现在怎么样，我该先做什么 | 四宫格 |
| 2 | **课题** | 主线 | 问题 → 假设 → 实验 → 结论 → 工艺窗口 | 烧瓶 |
| 3 | **证据** | 事实层 | 看清这次运行：条件、轨迹、结果、上下文 | 三层堆叠（= 标识的三块锭） |
| 4 | **追因** | 判断层 | 差异出在哪，证据够不够 | 带勾放大镜 |
| 5 | **配置** | — | 系统应该理解哪些变量、规则和设备 | 滑杆 |
| — | 系统管理 | — | 账号、健康与留痕（顶栏齿轮） | 齿轮 |

**四个关键决策：**

- **课题提到第二位。** v1 把「工艺研发」放在第 4 位，等于把产品的主线埋在中间。
  研发工程师每天的第一个动作是"打开我在推的那个课题"，不是"翻运行列表"。
- **「生产」+「质量」合并为「证据」。** 一次运行的条件、轨迹、结果、上下文本来就是一体的
  （`design.md` 的证据主干原话）。拆成两个模块，用户要在两个地方拼一次运行的全貌。
  「质量」这个名字还会让人误以为是 QMS —— 它做的是**实验的因变量测量**。
- **「质量追因」→「结果分布」移入追因。** 它做的是描述性分层，不是追因。原「超差追踪」删除（QMS 行为）。
- **「复核队列」降级为检测任务页的筛选状态。** 量产才需要两拨人的队列；研发是"同一个人隔天再看一眼"。

> **已知代价：**「证据」比「运行」抽象，日常"我要看昨天那次运行"要多想半秒。
> 缓解手段有三个：状态栏常驻入口、⌘K 直接搜运行号、决策工作台上每条记录都可点进运行详情。
> 若三个月后使用数据显示大家仍在找「运行」，把模块标签改回「运行」即可 —— 分组和路由不用动。

## 3. 命名规范

### 3.1 术语表（强制，出现在菜单、标题、正文、按钮、API 文案的同一个词必须一致）

| 统一术语 | 含义 | 禁止的同义漂移 |
|---|---|---|
| **运行** | 一次可分析的生产执行（`OperationRunId`） | 周期、生产周期、批次执行、cycle |
| ~~周期~~ | **已弃用**。模压场景中它和"运行"是同一件事（已确认） | UI 全面不出现"周期"；`CorrelationId` 仅作技术别名 |
| **实际值** | 从设备回读的真实值 | 设定值、目标值 |
| **设定值** | 配方声明的值 | 实际值 |
| **候选原因** | 观察分析提出、尚未验证 | 根因、原因 |
| **假设** | 已进入研发项目、可证伪 | 猜想 |
| **结论** | 经受控实验支持或否决 | 结果 |
| **工艺窗口** | 已验证 + 已声明适用范围与失效条件 | 最优参数、推荐配方 |
| **建议** | 机器提出、未生效 | 决定、方案 |
| **批准** | 人做出的、生效的决定 | 确认、提交 |
| **证据不足** | 识别条件不满足，不是失败 | 未知、无、不显著 |
| **分析准入** | 是否够格进入正式分析 | 数据质量合格 |

#### 3.1.1 运行的唯一身份（由"周期 = 运行"确认推出）

既然一次运行就是一个周期，界面上**只能有一个主标识**，其余全是技术别名：

| 标识 | 在界面上的地位 | 出现位置 |
|---|---|---|
| `OperationRunId`（运行号 `OR-…`） | **唯一主标识**。列表、详情标题、面包屑、引用、导出文件名都用它 | 全站 |
| `CorrelationId`（`CY-…`） | 技术别名，只用于排查现场上送问题 | **仅**证据面板的"来源"段与节点诊断页 |
| `RunKey` | 实验计划与真实执行之间的关联键 | **仅**实验详情与证据面板 |

**由此产生一个必须修的现存问题**：路由 `/cycles/:correlationId` 用关联号做详情页的键，
等于把技术别名提到了 URL 里。目标是 `/production/runs/:runId`，运行详情页保留"按关联号查找"的入口。

> ⚠️ 需要后端配合：`GET /runs?correlationId=` 反查接口。
> **代码补丁中路由参数暂时仍为 `:correlationId`**，以免 `CycleDetailPage` 立刻失效（已在文件里标了 TODO）。
> 待反查接口就绪，改成 `:runId` 并加一条 `:correlationId → :runId` 的重定向即可，属于第三期动作。

### 3.2 菜单命名规则

1. **名词短语，2–5 个汉字。** 菜单是地点不是动作。
2. **不用"管理"二字。** "质量管理""系统管理"——管理是废话，「质量」已经足够。（唯一例外：顶栏的「系统管理」，因为它确实只做管理。）
3. **不用"工业""智能""AI"等修饰词。** 在工业软件里这些词零信息量。
4. **父子不重名。** 模块「工艺研发」下不能有菜单「工艺优化」——现已改为模块「研发」下的「优化项目」。
5. **能力边界写进名字。** 「分析助手」而不是「AI 助手」。
6. **分组标签是任务，不是对象类型。** 「证据准备 / 差异分析 / 提问与核对」优于「对比 / 数据 / 问答」。

### 3.3 按钮文案规范

**总规则：动词 + 宾语，≤6 个汉字，一个视图只有一个主按钮（primary）。**
禁止出现裸的「提交」「确定」「保存」「OK」「操作」。

| 类别 | 规则 | 正例 | 反例 |
|---|---|---|---|
| 创建 | 从零用「新建」，加入已有集合用「添加」 | 新建工艺模型 / 添加装配位置 | 创建 / 新增 / + |
| 状态迁移 | 用业务动词，不用技术动词 | 提交复核 / 冻结分析数据集 / 发布工艺窗口 | 保存 / 更新状态 |
| 分析计算 | 用「生成 / 计算 / 重算」，暗示可重复 | 重算对比 / 生成候选假设 | 运行 / 执行 / 开始 |
| **机器提议** | 用「请求 / 生成 / 建议」，**永不用**「优化」「获得最优」 | 请求实验建议 / 换一批候选 | 一键优化 / 智能推荐 |
| **人的决定** | 用「批准 / 采纳 / 驳回 / 标记」 | 批准并排入实验 / 驳回候选 / 标记为证据不足 | 确认 / 同意 |
| 证据 | 明确产物 | 导出证据包 / 复制引用 | 导出 / 分享 |
| 危险 | 红色 + 二次确认 + 确认框说明影响范围 | 停用账户 / 作废配置版本 | 删除（无宾语） |

**最重要的一条：机器动作和人的决定必须用不同的动词族，并且视觉上可区分。**

- 机器提出的东西：虚线边框标签 `机器建议 · 未生效`，动作按钮用「请求 / 换一批 / 拒绝并说明理由」
- 人确认的东西：实线填充标签 `人已确认`，动作按钮用「批准 / 采纳 / 发布」

这直接落实 `design.md` 的"工程师保持控制"——不是靠文档，是靠按钮长什么样。

### 3.4 空态与拒绝文案

系统必须能体面地说"不知道"。这是产品的核心诚实性，不是边角情况。

| 情形 | 文案模板 |
|---|---|
| 证据不足 | 「证据不足：{因素A} 与 {因素B} 完全重叠，观察数据不能分离。需要 {缺少的格子} 才能拆开。」 |
| 数据缺口 | 「{时间段} 无过程数据，{N} 次运行不能进入正式分析。原因：{原因}。」 |
| 未接入 | 「{字段} 已在场景包中声明但从未上报。这是**未知**，不是已排除。」 |
| 未达门槛 | 「{N}/{M} 次运行未通过分析准入。它们保留在运行记录中并显示原因，不会被静默丢弃。」 |

### 4.1 Shell 骨架

```text
┌──────────────────────────────────────────────────────────────────────── 52px
│ ▣ Ingot │ 分析范围：[对象▾][设备▾][配方▾][时间▾] 🔒已锁定 │ 🔍⌘K  🔔 ◐ ⚙ (ZG)
```

**每一条都有理由：**

| 结构 | 尺寸 | 为什么 |
|---|---|---|
| 图标轨 | 56px | 6 个模块常驻可见且不占横向文字空间。原设计的顶部横向导航在 1366px 屏上会挤压面包屑 |
| 二级导航 | 228px | 最长菜单项「组件分类」+ 分组标签可完整显示，不截断 |
| 主内容区 | max 1600px | 表格类页面需要宽度；超宽屏不无限拉伸导致行首行尾视线跳跃 |
| 证据面板 | 376px | 默认收起，`⌘I` 或点任意"证据"入口唤出。宽度足以放下哈希与运行号不换行 |
| 状态栏 | 28px | 承载"数据还在进来吗"——一个 24 小时都成立的问题，不该需要点进某个页面 |
| 顶栏 | 52px | 让位给全局分析范围轴 |

### 4.2 全局分析范围轴（顶栏）

**这是本次重构最重要的新增结构。**

系统的全部方法论——可比运行、分层统计、因素重叠、混杂判断——都建立在
"我现在在看哪一批数据"之上。当前界面把这个概念散落在每个页面各自的筛选器里，
切页面就丢失，也无法在页面之间传递。

- 四个维度：**对象 / 设备 / 配方版本 / 时间范围**
- 🔒 **锁定**后，切换页面保持不变；解锁则每页可独立筛选
- 范围变化时，所有下游数字**同时**变化，并在状态栏刷新"分析准入率"
- 分析、对比、导出的证据包中都记录当时的范围快照

**取舍**：增加一个全局状态，实现成本不低（需要一个 ScopeContext + 各页面接入）。
但没有它，"可比"这件事只能靠用户自己在脑子里记住，而这正是 Ingot 想要消灭的东西。

### 4.3 五类页面模板

| 模板 | 用途 | 结构 | 适用页面 |
|---|---|---|---|
| **T1 列表 + 详情** | 逐条处理 | 筛选条 → 主表（可多选）→ 右侧详情卡 | 运行记录、检验任务、生产事件、复核队列 |
| **T2 台账** | 主数据 CRUD | 筛选条 → 全宽表 → 下方"选中项明细 + 变更影响" | 全部配置页 |
| **T3 分析画布** | 看差异、下判断 | 范围卡片行 → 结论边界横幅 → 主图 → 明细表 → 候选卡片；右栏放准入检查与可复现信息 | 运行对比、数据可信度、质量分布、超差追踪 |
| **T4 项目工作区** | 推进多阶段工作 | 顶部阶段步进条 → 左主栏（假设 / 建议 / 实验）→ 右栏（目标与边界 / 排程 / 已验证结论） | 优化项目详情 |
| **T5 仪表盘** | 分诊 | Hero 数字 + KPI 行 → 行动队列 → 趋势图 + 健康度 | 决策工作台、实时运行 |

**T3 的固定顺序不可打乱**：`范围 → 边界 → 图 → 明细 → 候选`。
先说这次比较的是什么、结论能走多远，再给图。
把"结论边界"放在图**之前**是刻意的——放在后面没人看。

## 5. 设计令牌

### 5.1 三色分工，互不重叠

`brand.md` 的色板释义是这次配色的唯一依据：

| 品牌色 | brand.md 原文用途 | 本设计的落法 |
|---|---|---|
| Evidence Gold `#E8AD56` | 建议、行动和主要强调 | **机器建议与「需要人做决定」**：建议卡片、待批准/待复核/待确认徽标、批准/采纳/发布按钮 |
| Trajectory Cyan `#5FD4C8` | 过程、连接与可信状态 | 过程轨迹主序列、数据可信度、连接与在线状态 —— **数据语义，不是交互** |
| （非品牌）Accent Blue `#2a78d6` | — | **交互**：链接、导航选中态、通用主按钮（新建 / 开始 / 打开 / 导出） |
| Deep Coal `#07100E` | 主背景 | 深色主题的页面底 |
| Process Panel `#0E1D19` | 卡片与数据面板 | 深色主题的卡片面 |
| Fog `#EEF5F1` | 深色背景文字 | 深色主题主文字 |

**核心规则：一屏上金色出现几次，就等于有几件事等你。**

这不是修辞，是可执行的约束：金色**不做通用主按钮色**。"新建工艺模型""导出证据包""开始对比"
这类动作用蓝色主按钮或中性描边按钮。只有 `批准` / `采纳` / `确认并发布` 这类**人的决定**穿金色。
青色也不做交互 —— 它只出现在过程曲线、可信度条、"数据在线"这类**说明数据本身**的地方。
标识释义本身就是这个意思 —— 顶部金锭 = 从证据中形成、仍可追溯的**当前判断**。

> 与上一版（v2.0）的差异：v2.0 判断"琥珀在工业界面里等于警告，所以只做身份不做交互"。
> 那是在没读 `brand.md` 的情况下做的判断，与规范冲突。现在的解法两边都守住了：
> 金色确实是"行动色"（符合规范），但把 warning 让给橙红一侧，两者不再打架。

### 5.2 五态语义 + 一个决策色

| 语义 | 含义 | 浅色 / 深色 | 图标 |
|---|---|---|---|
| 合格 / 已支持 | 通过、假设被实验支持 | `#0ca30c` / `#22b322` | ✓ |
| 需注意 | 临界、数据缺口 —— **可修的问题** | `#e2703a` / `#ef8a55` | ⚠ |
| 超差 / 已否决 | 失败、假设被否决 | `#d03b3b` / `#e05252` | ⊗ |
| **证据不足** | **识别条件不满足 —— 不是可修的问题** | `#8b97a3` **灰 + 45° 斜纹** | ? |
| **待你决定** | 需要人做判断 | **Evidence Gold `#E8AD56`** | ◈ |
| 机器建议 | 未生效的提议 | 金色**虚线**边框，透明底 | — |
| 人已确认 | 生效的决定 | 金色**实线**边框，填充底 | ✓ |

> **"证据不足"必须是灰色带纹理，不能是橙也不能是金。**
> 橙色（需注意）意味着"补上数据就好了"；金色意味着"你来定"。但证据不足两者都不是 ——
> 它是"在现有识别条件下这个问题问不出答案"，正确的下一步是**设计实验**，不是补数据也不是拍板。
> 灰色 + 斜纹让它在视觉竞争中主动退出，纹理保证在色盲、灰度打印和 `forced-colors` 下仍可辨。
> 同一处理用于因素重叠矩阵的空格 —— 空格是"不可分离"，不是"零次运行"。

**默认主题：浅色。** 深色用 `brand.md` 的原值（Deep Coal / Process Panel / Fog），是一等公民不是降级版。
分析工作长时间读表读数，浅色更省眼；车间节点与大屏用深色。两套都通过了调色板校验。

### 5.3 图表规范

调色板已用 `dataviz` 的验证脚本在两种主题下跑通全部硬门禁
（浅色底 `#ffffff`、深色底 `#0E1D19` = Process Panel；两边全部 PASS。浅色下槽位 4/5 对比度低于 3:1，触发 relief 规则 —— 必须配可见直标或表格视图，本设计一律直标）。

| 槽位 | 浅色（底 `#ffffff`） | 深色（底 `#0E1D19`） |
|---|---|---|
| 1 青（过程） | `#0f9c90` | `#2da096` |
| 2 橙 | `#eb6834` | `#d95926` |
| 3 蓝 | `#2a78d6` | `#3987e5` |
| 4 黄 | `#eda100` | `#c98500` |
| 5 品红 | `#e87ba4` | `#d55181` |
| 6 紫 | `#4a3aa7` | `#9085e9` |

> 槽位 1 是青色，因为过程轨迹是这个系统最常画的东西，而青正是 brand.md 给"过程"的颜色。
> 深色槽位 1 用 `#2da096` 而不是品牌原值 `#5FD4C8` —— 后者亮度 0.80，超出图表可用亮度带
> （校验脚本 FAIL）；`#5FD4C8` 仍用于文字、图标与选中态，那里它是合适的。

**硬规则：**

- 分类色**按固定顺序分配，绝不循环**。第 9 条序列不生成新色，折成"其他"或做小倍数图。
- **永不使用双轴**。两个量纲 → 两张图、小倍数图，或统一指数化。
- 顺序色 = 单一色相由浅到深；发散色 = 两个色相 + 灰色中点。绝不用彩虹。
- 线宽 2px，端点标记 ≥8px 带 2px 底色描边；网格 1px 实线、贴近底色；柱条 ≤24px、数据端 4px 圆角。
- ≥2 条序列必有图例；直标**选择性**使用（端点 / 极值 / 故事主角），**端点标签相撞时整体撤掉**，交给图例 + 悬停。
- 文字永远用文字色，绝不穿序列色。
- 状态色是保留色，绝不当作"第 4 条序列"；且必须**图标 + 文字**同时出现。
- 所有折线/面积图默认带十字准线 + 悬停提示；柱/点/单元格带逐标记提示。

## 7. 四个关键交互

### 7.1 证据面板（`⌘I`）
界面上任何一个数字都必须能追回它的来源。面板固定四段：
**这条结果从哪来**（运行 / 实际条件 / 质量结果 / 上下文快照）→
**版本与可复现**（分析模型、工艺模型、场景包、输入哈希、冻结数据集）→
**这条证据不能说明什么** → **导出证据包 / 复制引用**。

第三段是关键。系统主动声明自己的边界，比事后被工程师戳穿要好得多。

### 7.2 对比暂存区
工程师看到可疑运行的时刻，和他想做对比的时刻，往往隔着好几个页面。
暂存区在状态栏常驻显示计数，跨页面保留，随时「开始对比」。
成员可标记为**基线组 / 对照组**，并在加入时即时提示是否满足分析准入。

### 7.3 命令面板（`⌘K`）
从"页面搜索"升级为三段式：**动作**（发起运行对比、请求实验建议、冻结数据集、导出证据包）、
**对象与运行**（运行号、项目号、模型编码、组件编号直达）、**页面**。
动作条目的描述里写明它是否需要批准。

### 7.4 机器建议 → 人的批准
建议卡片必须同时给出：**建议值 + 当前值 + 允许范围 + 理由 + 不确定区间 + 满足约束的概率 +
模型版本与随机种子 + 已避让的待执行点**。
底部四个动作：`拒绝并说明理由` · `换一批候选` · `导出执行单` · **`批准并排入实验`**（主按钮）。
拒绝理由被记录——它是评估建议质量最有价值的数据，当前系统完全没有采集。

**单人批准（已确认）。** 一个有权限的工程师即可批准，不设第二审批人。
这个决定让实验排程的状态机保持简单，但也意味着**留痕是唯一的控制手段**，
因此以下三条从"最好有"升级为"必须有"：

| 要求 | 具体做法 |
|---|---|
| 批准即快照 | 点下「批准并排入实验」的瞬间，冻结当时的建议值、约束、模型版本、种子、输入哈希与分析范围。后续模型升级不改写这条批准记录 |
| 理由强制 | `拒绝并说明理由` 的理由框**必填**；`批准` 的理由框选填，但若批准值偏离建议值则**转为必填** |
| 全部进审计 | 批准/拒绝/修改安全边界三类动作直接写入 `/system/audit`，可按人、按项目、按时间检索 |

实验状态机因此保持六态，**没有"待他人审批"**：
`草案 → 待批准 → 已批准待执行 → 执行中 → 已结束`，外加旁路的 `已作废`。

> 若将来引入分级审批，只需在 `待批准` 与 `已批准待执行` 之间插入一个状态，
> 界面上是给建议卡片加一个 `提交上级审批` 次按钮——结构不必推倒重来。

## 8. 迁移路线

分三期，每期可独立上线、独立回滚。

### 第一期：导航层（1–2 周，风险低）
- 落地新 `App.jsx` 导航结构 + 全部旧路由重定向
- 落地新设计令牌（`tokens.css`）与 `ui/components.jsx` 样式统一
- 页面内容零改动
- **验收**：所有旧链接可达；新菜单可完成全部旧任务；无控制台错误

### 第二期：全局结构（3–4 周，风险中）
- `ScopeBar` + `ScopeContext`，各页面接入
- `StatusBar`、`EvidencePanel`、`ComparisonBasket`、升级版 `CommandPalette`
- `StatusTag` 七态与 `ProvenanceTag` 全站替换
- **`/system/audit` 审计追踪页提前到本期**——单人批准模式下它是唯一的控制手段
- **验收**：范围锁定后跨页保持；任意数字可打开证据面板；证据包可导出；每一次批准/拒绝/改边界都能在审计页查到

### 第三期：页面重做（6–10 周，风险高）
按价值排序，逐页迁到五类模板：

1. 运行对比（T3）— 系统的核心，当前最难用
2. 优化项目工作区（T4）— 118KB 单文件，最该拆
3. 决策工作台（T5）
4. 数据可信度（T3）

## 10. 决策记录与剩余开放问题

### 10.1 已确认（2026-08-04）

| # | 问题 | 结论 | 已落到规格的哪里 |
|---|---|---|---|
| 0 | 产品定位是什么？不是 MES 的话是什么？ | **工艺参数决策的证据系统**：DOE 统计软件 + 电子实验记录本的交集，唯一产出物是有适用范围与失效条件的工艺窗口 | §0 定位口径；§0.1 三条硬约束；一级导航按事实层/判断层重划为 5 模块 |
| 0b | 要不要做班组？ | **班组管理不做**（MES 地盘）；**"班次"维度删除**（研发试制阶段是常数）；**"执行人"保留并升级**为可比性检查里的报警项 | §0.1 第 3 条；场景包页面演示"上下文维度不硬编码"；原型里 `班次` 已全部替换为 `执行人` |
| 0c | 品牌色板与交互色冲突怎么办？ | **金色 = 需要人做决定**（不是通用主按钮色），青色 = 过程与可信状态，warning 让给橙红 | §5.1 / §5.2；`global.css` 令牌；原型里金色出现次数 = 待决事项数 |
| 1 | 「周期」和「运行」是同一件事吗？ | **是。** 模压场景中一次运行 = 一个周期 | §3.1 把"周期"标为已弃用；§3.1.1 定下运行号为唯一主标识，`CorrelationId` 降为技术别名；UI 全站不再出现"周期" |
| 2 | 实验需要几个人批准？ | **一个人即可**，不设第二审批人 | §7.4 单人批准 + 三条强制留痕；实验状态机六态无"待他人审批" |

> 决定 1 带出一个需要后端配合的动作：详情页的键从 `correlationId` 换成 `runId`，

> 决定 2 带出一个必须做的动作：`/system/audit` 从"第三期新增页"提前——
> 它是单人批准模式下唯一的控制手段，建议随第二期一起上线。
